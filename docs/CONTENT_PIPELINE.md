# Data-driven content and long-term architecture
Canonical stable IDs, JSON schemas and validation at build/startup. Content packs define ingredients (states, transitions, asset refs, cost), recipes (required multiset, allowed quality, price), stations (verbs, capacities, timing, sockets), layouts (grid, zones, spawn/approaches), customer profiles (patience, queue, tip), days (recipe unlocks, spawn schedule, target), upgrades (cost, prerequisites, effect), restaurants (theme, levels, progression), challenges (objective, seed, constraints). Runtime systems interpret records; no Burger Town branches in simulation except test fixtures. Add a new verb through registered typed handler with tests, not arbitrary executable JSON. Separate rules from presentation asset registry and locale strings. Validate duplicate IDs, references, reachability, numeric ranges, recipe satisfiability, unlock DAG and asset status per gate. Reject unknown schema versions with actionable error. No dynamic remote executable content.

## Content workflow
Author data → schema validation → dependency/asset audit → deterministic simulation scenarios → in-engine visual check → human playtest → versioned pack release. Add one restaurant vertical increment at a time after G2. New restaurant template includes level layout, palette/material variants, recipe set, new mechanic and tests; use same core systems. Little Italy adds oven timing/batch capacity; Tokyo Street adds precision prep; Asian Night Market adds multi-step broth; Tropical Paradise adds demand events; Grand Metropolitan adds quality/modifiers. These are proposed later scope, not authorized implementation. Preserve stable IDs across saves; deprecate with migration mapping; never silently delete a recipe referenced by saves. Save schemaVersion/contentVersion/buildVersion, backup before migration, validate old fixture. Challenge/endless/sandbox namespaces independent. No offline income. Manager simulation later capped per in-game day and seeded.
