# Live preview and release workflow
From M1 G1, deploy an explicitly labeled prototype preview only after Producer authorizes publication, repository visibility, asset rights and hosting. GitHub Pages is static; no backend. Free public repository option; private Pages/Actions availability depends on plan. Never change visibility or incur fees without approval. One Pages site per repo; use a dedicated preview repo only if authorized, otherwise same site with clear preview label until release. PR checks upload dist artifact but do not publish PRs. Use manual workflow_dispatch on approved main commit or reviewed rollback tag. GitHub Settings > Pages > Build and deployment > GitHub Actions; protect github-pages environment with required reviewers where supported; otherwise manual dispatch by authorized Producer. Templates under templates/github-actions are intentionally inert until M0 adopts them, pins reviewed action versions and verifies scripts. Do not copy deploy template to active workflow until authorized. Vite base is /<repo>/ for project Pages, / for user site/custom domain; configure via environment and asset URLs via import.meta.env.BASE_URL. Hash routing if needed. See https://vite.dev/guide/static-deploy and https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages.

## Version and evidence
Embed build version, commit SHA, content/save schema version and PREVIEW label in menu/results. CI stores reports, screenshots and dist tied to commit; capture actual URL from deploy action, run deployed smoke (HTTP, JS/CSS/GLB URLs, MIME, no console errors, start/play/restart) and record commit/browser/date. A successful deploy action is not proof gameplay works. Do not claim URL before deploy and smoke. Use semver tags v0.1.0-preview.1 etc; release G4 separate. Never auto-merge. Rollback dispatch reviewed prior known-good tag from main workflow, confirm rights, rebuild locked dependencies, check save compatibility; if newer save incompatible, preserve backup and warn before restore. Smoke again; record rollback commit and reason. No destructive reset.

## Feedback loop
Producer plays URL → opens GitHub issue using template (version/URL/browser, steps, expected/actual, screenshot/video, severity, acceptance test) → triage P0 blocker/P1 major/P2 minor/P3 polish → Codex reproduces with seed/save fixture → fixes scoped branch, adds regression, CI, PR → Producer reviews → authorized deployment → retest issue and close only with evidence. Design requests update GDD/decision log first. Maintain release notes and open defects; protect working features. No automatic publication without permission.

## M1 Pages candidate

- Build and run Playwright with `VITE_BASE_PATH=/kitchen-chaos-3d/`. Set `VITE_BUILD_SHA` to the full reviewed commit SHA. The version footer and menu/results show the embedded build identity. The PR CI artifact is `dist-<sha>`.
- Confirm the original graybox asset ledger and record separate Producer authorization for the reviewed SHA and public Pages audience. Use the standard project subpath for this repository. A custom domain would require a root-base rebuild and smoke.
- After authorization, enable GitHub Actions as the Pages source and activate [the prepared dispatch workflow](../templates/github-actions/pages.yml). Protect the `github-pages` environment where supported. Dispatch from main with the reviewed full SHA and approval reference. Use a commit reachable from main.
- Record the deployment URL and workflow run. After the workflow confirms the deployed build identity, verify the deployed URL in Chromium. Confirm healthy JS, CSS and JSON responses and no console errors, start a shift, deliver a Classic burger, pause and restart.
- Roll back by dispatching with the previous approved, reachable SHA and its approval reference, then repeat the hosted browser smoke. M1 has in-memory sessions. Refreshing the page returns to a fresh shift.
